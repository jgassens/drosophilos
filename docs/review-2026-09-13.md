# Review of the DrosophilOS plan (2026-09-13)

> Author: Jeremiah Gassensmith. Archived verbatim. The plan in `docs/plan.md` is the
> revision that resulted from this review (its twelve numbered changes map onto the twelve
> sections below).

**The largest change I would make is to move a small connectome-constrained demonstration into Stage A/B rather than waiting for Stage H.** As written, the project could complete its compiler, neural renderer, and distributed execution system before discovering whether the resulting circuits can be embedded in fly wiring. Stage H currently carries the uncertainty most central to the name and scientific premise of DrosophilOS.

I would retain the computational boundary, explicit substrate profiles, exact-versus-approximate data classes, and measured circuit contracts. Those give the project a testable definition. The main revisions concern dependency order, communication correctness, simulator validation, and several places where an implementation detail could inadvertently move computation back onto the host.

## 1. Bring a small part of Stage H forward

Developing freely synthesized circuits first is sensible. Developing the *entire machine* before testing constrained placement is not the sequence I would choose.

My proposed addition is **Stage H0: embed and compose a minimal native-topology circuit**, running alongside Stage A. Its target should be modest: an input buffer, a register, an arithmetic or comparison operation, a completion detector, and a return path. It should use actual MCNS neuron IDs, preserve the declared connectivity constraints, and operate with surrounding circuitry present.

This answers three consequential questions early:

Does the graph contain usable implementations of the necessary motifs? Can they be connected without excessive relay overhead? Can they operate without uncontrolled interference from surrounding neurons?

The result need not be a complete processor. Even finding that registers embed efficiently but reliable handshakes require disproportionate circuitry would change the compiler and allocation strategy.

There is also an internal inconsistency in the profile definition. Profile 2 permits silencing, but the manifest says added, suppressed, and rerouted connections must all be absent for Profile 2. These cannot both hold without a sharper definition of "suppressed."

I would distinguish **structural changes** from **parameter changes**. Profile 2 could prohibit added or rerouted anatomical edges while allowing explicitly documented zero weights or silenced cells. The manifest should report the original graph, retained graph, active nonzero graph, and every silencing intervention separately.

That matters scientifically: preserving an anatomical adjacency matrix while setting most inconvenient connections to zero is a different achievement from operating successfully within a largely active surrounding network. Both can be investigated, but their resource and intervention costs should remain visible.

## 2. Netlist mode is useful, but "exact" needs qualification

The plan describes netlist mode as simulating the program neurons plus a permitted neighborhood, and labels it "fast, exact, deterministic." Full-graph mode is then used to test interference.

**A truncated network is not automatically equivalent to the full network.** For a retained neuron \(i\), its input can be separated into

\[
I_i(t)=I_i^{\mathrm{retained}}(t)+I_i^{\mathrm{omitted}}(t).
\]

Deleting the second term changes the model unless it is demonstrably zero, faithfully reproduced, or bounded tightly enough not to change the architectural result.

A one-hop or two-hop neighborhood does not settle this: omitted neurons may influence retained neurons through longer recurrent paths.

I would describe netlist mode as **isolated execution of the compiled circuit**, then add a separate classification for its relationship to the full graph:

"Equivalent under stated isolation assumptions," "robust within a measured boundary-input envelope," or "not yet assessed."

For Profile 2 tests, measure the boundary inputs reaching the circuit in full-graph runs and challenge the isolated circuit with those inputs. Include coordinated bursts and structured activity, not only independent Poisson background. The latter is in the current perturbation plan but should not become the sole representation of interference.

Similarly, full-graph mode needs a declared model for surrounding nonspiking cells even when those cells are not intentionally used by a primitive. "Only when a used primitive needs one" leaves their contribution to the interference test underspecified.

## 3. The handshake is the first correctness problem to fix

The stated protocol ends with an ACK followed by the producer clearing its transaction state. It does not specify how the receiver's bit latches reset, how completion logic returns to its initial state, or how the producer learns that the receiver is ready for another word.

That omission can corrupt the next transaction even when every arithmetic circuit works.

Conventional four-phase dual-rail handshaking includes both data acknowledgment and acknowledgment of the return to the empty state. A new transfer begins only after that cycle completes. Spiking signals need an explicit neural implementation of the corresponding state transitions; they do not provide them automatically.

I would specify something like:

```text
DATA(n) → VALIDATE(n) → ACCEPT(n)
        → RESET transaction storage
        → RESET_COMPLETE / READY(n+1)
```

Those names describe neural protocol states—not Python callbacks.

The other missing foundational primitive is a **state-holding completion element**, analogous to a Muller C-element. Such an element changes state when its inputs agree and otherwise retains its previous state. That behavior is different from a coincidence detector responding to spikes that happen to overlap.

For DrosophilOS, it should operate on latched input-valid states. I would implement and verify that before assembling large arithmetic circuits.

The protocol contract also needs to settle these cases: a delayed opposite-rail spike after apparent completion; a duplicate arriving after reset; a lost ACK; a fork whose consumers finish at different times; and a branch whose unselected output never produces a token. In particular, a branch merge must not wait for both mutually exclusive paths.

I would initially call this a **bounded-delay, self-timed spike protocol**, not a delay-insensitive implementation. Finite retention, timeouts, and locally generated evaluation windows already impose timing assumptions. Stronger terminology should follow a proof of the actual protocol, not follow automatically from using dual rails.

## 4. Strengthen simulator verification at the spike and transaction levels

The proposed Brian2 comparison—rates within 1%—is inadequate for validating this machine. Two simulations can have identical spike counts and still disagree about coincidence, token order, or whether an interrupt precedes a commit. The current verification also combines bit-exact CPU parity, floating-point CPU/CUDA tolerance, and determinism across batch sizes without distinguishing their purposes.

The key numerical hazard is:

\[
V=\vartheta-\epsilon
\quad\text{versus}\quad
V=\vartheta+\epsilon.
\]

Those values can pass a floating-point closeness test while producing different spike events.

I would require three levels of comparison: membrane/synaptic trajectories, spike-event traces, and decoded architectural transactions. The last level must match exactly for the exact ISA, even when small permitted numerical differences exist underneath.

Before writing the reference steppers, specify the complete within-step order: event delivery, synaptic updates, membrane integration, threshold detection, reset, and refractory handling. Brian2 explicitly exposes scheduling order, and its default places threshold detection before synaptic event processing within a timestep. Matching differential equations without matching event scheduling does not define the same discrete simulation.

PyTorch also does not generally guarantee bitwise agreement across CPU/GPU execution, platforms, or mathematically equivalent batched and unbatched operations. Deterministic algorithms are useful, but do not erase those distinctions.

My preferred baseline would be a carefully specified float64 CPU reference, followed by backend-specific certification against architectural outputs. Add timestep-refinement tests: a circuit that works at 0.1 ms but fails under finer integration may be exploiting the simulator's scheduling or quantization rather than a robust neural mechanism.

The "1–2 days" estimate is reasonable as a repository-and-smoke-test estimate. I would not attach it to validation of the simulator itself.

## 5. DrosoC needs a semantic specification, not just a parser

The compiler path is sensible, but **"the same source compiles with clang unchanged" is not sufficient to establish a golden reference**. Your ISA promises explicit wrapping, saturation, signedness, and fixed-point behavior; ordinary C expressions do not automatically have those semantics.

Signed overflow and invalid shifts are among the behaviors Clang's undefined-behavior sanitizer specifically detects. A wrapping neural add cannot be compared uncritically with an overflowing signed C expression.

I would define a small arithmetic interface whose portable C implementations and FlyISA lowering share the same specification. It should settle wrapping addition, saturating addition, multiplication rescaling, negative-value rounding, shifts, division by zero, and narrowing conversions.

For example, fixed-point multiplication needs more than "64-bit intermediate, then rescale." It must specify what happens to negative products between representable values and to rescaled products outside the destination range.

`pycparser` is a reasonable parser choice, but its own documentation states that it does not interpret type semantics. DrosoC still needs semantic analysis, integer promotions, symbol resolution, bounds validation, and rejection of unsupported constructs.

I would add an **executable FlyISA/IR reference interpreter** before neural lowering. Then debugging has three comparison points:

```text
portable C reference ↔ IR interpreter ↔ neural execution
```

The interpreter is a development oracle, not part of the reported neural runtime.

Finally, replace raw "state dump byte for byte" with **canonical serialized state equality**. Define field order, widths, byte order, and excluded padding explicitly. Otherwise, a comparison can fail—or pass for the wrong reason—because of host object layout rather than game semantics. The intended Stage D criterion remains exact equality.

## 6. Memory addressing and circuit composition need earlier resource tests

The one-decoder-neuron-per-word construction is a useful experiment, but not yet a scalable memory design.

A fully populated 16-bit word index would require **65,536 decoder neurons per bank** under that construction, before storage cells, readout, write control, or protection. The address format should remain a namespace; the compiler must instantiate only physically allocated capacity. I would test hierarchical predecoding alongside the flat decoder.

The proposed threshold \(b-0.5\) also has a useful worst-case implication. If each of \(b\) normalized matching contributions can be reduced by a fraction \(\epsilon\), a matching address requires

\[
b(1-\epsilon)>b-0.5,
\]

so

\[
\epsilon<\frac{0.5}{b}.
\]

For \(b=16\), that is a 3.125% worst-case uniform-reduction margin, before accounting for leakage or arrival-time differences. This is a calculation for the proposed construction, not an experimentally measured tolerance.

The primitive contracts should consequently include **fan-in, fan-out, supported load, background-input envelope, reset latency, and maximum outstanding transactions**, in addition to the fields already listed. Otherwise, two individually passing circuits may fail when connected.

This also affects the work split. Bit-cell, adder, and port-codec development can proceed in parallel only after their shared token, reset, timing, and loading interfaces are fixed. They are not independent at the interface level, even though their internal implementations can be developed independently.

## 7. Make the first renderer exact; treat population coding as an optimization

The plan introduces population-vector heading and transforms while allowing bounded-error rendering with exact fallback. That is a worthwhile research direction, but I would not make it part of the first successful renderer.

A winner-take-all margin is not, by itself, a bound on coordinate error. Nor does a small angular error automatically imply a small rendering error.

For the proposed projection

\[
u=u_0+f\frac{y_c}{x_c},
\]

first-order error propagation gives

\[
|\delta u|
\lesssim
f\left(
\frac{|\delta y_c|}{|x_c|}
+
\frac{|y_c|\,|\delta x_c|}{x_c^2}
\right).
\]

Near the camera plane, modest coordinate uncertainty can produce a large pixel displacement. Texture addressing and visibility decisions introduce additional discrete boundaries.

I would split Stage E into **E1: exact renderer**, followed by **E2: population-coded acceleration with propagated uncertainty**. E2 should report how often fallback occurs and whether the accelerator still saves neural resources or time after including conversion, uncertainty handling, and fallback circuitry.

The population-vector contract also needs an explicit response to near-zero resultant magnitude. When two opposing vectors cancel, the resultant angle is not a meaningful value; the decoder should return an invalid/indeterminate status rather than a confident heading.

There is a separate naming issue in `minidoom`: because the plan specifies a from-scratch engine, agreement with its clang build demonstrates correct execution of *that engine*. It does not independently establish compatibility with the original Doom implementation. Keep the distinction between **a neural Doom-like engine** and **a neural port of Doom** visible in benchmark descriptions.

## 8. Add a whole-program capacity report before scaling the cluster

The plan measures neurons per RAM bit and ROM density, but it needs an early estimate of **total live storage and total instantiated circuitry for an actual workload**.

For illustration, the proposed 160 × 100, four-bit framebuffer contains

\[
160\times100\times4=64{,}000\text{ bits}.
\]

Using the plan's provisional 16-neurons-per-bit assumption, double buffering alone would require

\[
2\times64{,}000\times16=2{,}048{,}000\text{ neurons}.
\]

That is before addressing, protection, or rendering circuitry—and uses an unvalidated memory cost. A scanline or tile-streaming design could require much less retained pixel storage, but the choice should be explicit. The resolution and provisional bit-cell cost come directly from the plan.

Before a large cluster run, the compiler should report live game-state bytes, asset-ROM bits, arithmetic-unit counts, control and handshake overhead, spill storage, per-frame communication, and estimated critical-path latency.

The 2–3 k-line engine estimate does not answer those questions. A short source program can instantiate a very large spatial circuit, especially when loops or functions are expanded rather than reused.

I would therefore make resource sharing a first-class compiler choice early: whether a loop reuses an ALU, whether calls share a resident kernel, and whether rendering workers reuse a multiplier. This is too important to defer entirely to the Stage G interpreter.

## 9. The Python control plane is acceptable for development, but needs a defined endpoint

Labeling early orchestration as hybrid is correct. The omission is that no milestone clearly demonstrates removal of the Python control plane. Stage F explicitly retains it; Stage G establishes compilation inside a neural VM; Stage H assesses topology. None necessarily establishes a neural operating system.

I would add **Stage F2: neural execution control**. Its result should demonstrate that neural circuits determine work readiness, dispatch, authoritative commits, and application-level recovery for the supported configuration.

For the first version, static worker assignments and a fixed neural scheduler are sufficient. A general-purpose distributed hypervisor is not required to establish that the runtime decisions are neural.

There is also a host-boundary issue in FlyLink. External transport may attach a physical source-neuron identity, simulator timestamp, and predetermined route. It must not inspect a Python task object and supply an epoch or sequence value that the neural sender never represented. The current packet fields and endpoint requirements need a concrete wire-format specification explaining where each field originates.

A useful implementation rule would be: the production simulator and transport do not depend on game objects or ISA operation handlers. Diagnostic observers may inspect those abstractions during testing, but they must not become hidden runtime controllers.

Benchmark labels should keep four independent distinctions visible: substrate profile, isolated versus full-graph execution, hybrid versus neural orchestration, and external versus self-hosted compilation.

## 10. Fault tolerance and checkpoints need two separate specifications

"Raft-shaped" is appropriate as an architectural sketch, but not as a correctness specification. The original Raft model assumes non-Byzantine failures; a malfunctioning neural node that sends inconsistent valid-looking messages is not necessarily a crash failure.

The plan already identifies the crash model, so I would preserve that scope and explicitly state what converts neural computational faults into detected rejection or fail-stop behavior. Otherwise, TMR and the commit log can each appear to cover a failure that falls between their assumptions.

The voter, commit controller, and authoritative metadata also need protection. Replicating game computation while leaving the commit decision in one unprotected neural circuit is not end-to-end redundancy.

For the "without repeating a world update" requirement, persist request identity and the last applied transaction alongside state. Raft's client-interaction treatment specifically addresses the case where a command commits, the response is lost, and a retry would otherwise execute it twice.

Separately, I would remove the blanket prohibition on raw membrane checkpoints. **Architectural checkpoints and simulator checkpoints serve different purposes.**

Architectural checkpoints are the right mechanism for demonstrating portable recovery onto a replacement neural node. Full simulator snapshots are valuable for reproducible debugging and resuming interrupted HPC experiments. They need delayed events and other dynamical state; Brian2's restore mechanism explicitly preserves pending delayed spikes. Using such a snapshot during debugging does not establish biological recovery and should not be presented as doing so.

## 11. Keep \(10^{-10}\) as a reliability objective, not a prematurely measured claim

The plan correctly treats this as a protected architectural-operation target. However, the statement that it is "reached by redundancy and detection" needs to remain a hypothesis until the protection scheme and fault assumptions are quantified.

For zero observed failures in \(n\) independent Bernoulli trials, the one-sided 95% upper bound is

\[
p_{\mathrm{upper}}=1-0.05^{1/n}\approx\frac{3}{n}.
\]

Consequently, a zero-failure empirical demonstration near \(10^{-10}\) would require approximately **30 billion independent trials**. This follows from the binomial confidence-bound construction.

That does not preclude the reliability target. It means the report must distinguish observed error bounds, analytically predicted residual error, and results of structured fault injection.

I would emphasize proofs or exhaustive checks for small protocol state machines, bounded perturbation analysis for elementary circuits, and explicit common-mode failures in the redundancy tests. Multiple replicas with the same compiler error or shared timing defect are not independent trials.

Likewise, "retention to 10× the longest expected hold" is useful only if the machine defines a maximum supported hold. Backpressure can otherwise extend a nominally short transaction indefinitely. The timeout/recovery policy and memory-retention contract need to agree.

## 12. Correct two access assumptions and refine the simulation budget

**Data access is not necessarily blocked on a user token.** Janelia documents account-based API access, but also provides direct bulk-download files for annotations, neurotransmitters, and connectivity. The access item should begin with verification of that bulk route rather than assume interactive Codex access is required.

The same documentation says the full connection table covers all segments with synapses. The loader must explicitly define the neuron-selection and edge-filtering rules before expecting a particular connection count. Codex currently displays 166,700 MCNS neurons and 6,242,118 connections; that does not independently verify the plan's 25.5-million figure or establish identical filtering.

**H200 availability remains unverified.** UTD's publicly indexed Juno description lists A30 and H100 GPUs. The actual scheduler inventory, memory limits, and allocation—not the assumed H100/H200 queue—should determine physical mapping.

Finally, the approximately 2 TB connectivity estimate assumes storing 1,000 separate copies. Immutable topology can be shared among simulated nodes, while node-specific state and overrides remain separate. Under the proposed linear synapse model, contacts with identical source, destination, kernel, and delay can also be combined mathematically by summing weights. Different delays or independent synaptic dynamics cannot be discarded that way.

This does not make full-cluster simulation inexpensive. It means memory capacity, event-processing throughput, and achievable simulated time should be estimated separately rather than treating replicated raw contact storage as an unavoidable requirement.

## Revised milestone order

I would keep the existing stages but change their dependencies:

| Stage | Recommended adjustment |
|---|---|
| **0** | Specify event scheduling and arithmetic semantics; establish a reference simulator and data-loader smoke test. |
| **A1** | Implement token storage, completion, reset, register, and a small adder before the full primitive library. |
| **H0, concurrent** | Embed and compose a minimal circuit in MCNS; assess surrounding-network interference. |
| **A2/B** | Compile an input-dependent control-and-memory program; add the IR interpreter and resource report. |
| **C** | Demonstrate two-node communication, including reset, retries, stale events, and backpressure. |
| **D/E1** | Execute exact world updates and a small exact renderer before adding approximate accelerators. |
| **F/F2** | Scale by measured need, then demonstrate neural execution control without Python application orchestration. |
| **E2/G/H** | Add population acceleration, self-hosted compilation, and full-workload native-topology assessment as distinct results. |

**The first decisive demonstration should be a runtime-input-dependent program that stores a value neurally, performs arithmetic, takes a neural branch, sends a validated result to a second node, and emits a neurally computed pixel—with a parallel demonstration that the required circuit can operate in MCNS-constrained wiring.**

That would establish the foundations DrosophilOS actually depends on. Doom then becomes a demanding integration benchmark, rather than the first occasion on which the project discovers that its memory, handshake, compiler, or connectome assumptions do not compose.
